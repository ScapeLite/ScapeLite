## 2. Schema (`raid-trees.json -> delve`)

```
delve: {
  skill:"delve", name:"Delve",
  starter:{id:"delve_n0", tier:"large"},      // free root, NOT in nodes[] and NOT in allocated[]
  pointsFreeStart:1,                          // (not read by RaidTreeEffects; points = level, see 3)
  purchasable:120, basePurchasable:99, extendedPurchasable:120,
  clusters:[11], nodes:[120], layoutExtensions:[2]
}
node: {id:"delve_nK", tree:"delve", cluster, tier:"small|medium|large", effect, value, slot:K,
       requires:["delve_nP"],                 // always exactly ONE parent (the tree is a strict tree)
       skill?:"life|spirit|...",              // only effect "effLevel"
       head?:"+1 Life level",                 // display text for effLevel nodes
       requiresLevel?:100|110}                // minimum Delve level to allocate
cluster: {id,name,effect,unit,scope:"global|raid",desc,negative:false,total,nodeIds[]}
```
Example nodes: `{"id":"delve_n1","cluster":"cleave","tier":"small","effect":"minHit","value":1,"slot":1,"requires":["delve_n0"]}`, `{"id":"delve_n17","cluster":"battle_prowess","tier":"medium","effect":"effLevel","value":1,"skill":"life","head":"+1 Life level","requires":["delve_n16"]}`.

Facts verified by script:
- Node ids are `delve_n1..delve_n120` (slot == number); 120 purchasable nodes. Tiers: 66 small, 36 medium, 18 large (tier only changes the visual shape and the value size; value is per node, no ranks).
- No ranks, no keystones, no "special" effect types: each node is a binary on/off with one fixed `value`. `max rank` = 1. Large nodes are just bigger numbers.
- All 120 nodes have exactly one `requires` entry (0 multi-parent nodes): the graph is a rooted tree, max depth 14 from n0.
- Base tree = n1..n99 (`basePurchasable:99`, reachable at level <= 99). n100..n120 are the "extended" part: all 21 carry `requiresLevel` (100 or 110). They hang off two spots only: chain n100-n110 under n68 (branch 7) and chain n111-n120 under n40 (branch 3).
- `requiresLevel` nodes (21): level 100 = n100-n104, n111-n115; level 110 = n105-n110, n116-n120.

## 3. Cost, points, validation, respec (bundle @206800-207030 and RaidTreeView @~1514900)

- Cost: every node costs exactly 1 point. Currency = talent points, **not** credits/gold.
- Points owned: `pointsAvailable(level) = Math.max(0, level || 1)` -> total points = Delve level (level 1 = 1 point, level 99 = 99, level 120 = 120). Spent: `pointsSpent(allocated) = allocated.length`. Free points = level - allocated.length. Points come only from leveling Delve (XP from raid damage, see `delveXpPct`).
- Allocate (`validateAllocate(tree, nodeId, allocated, level)`), checked in this order:
  1. `unknown_node` (node missing or wrong tree)
  2. `already_allocated`
  3. `level_required` if `node.requiresLevel && level < node.requiresLevel`
  4. `no_points` if `allocated.length >= max(0, level)`
  5. `prereq` if `!prereqsMet`: every id in `node.requires` must equal the starter (`delve_n0`, always satisfied) or be in `allocated`.
  Client then sends `L.send("allocate_talent", {tree:"delve", nodeId})`. Server-side validation presumably identical (shared module) - not directly observed.
- Connectivity rule: because each node has exactly one parent, a legal allocation is exactly a set closed under "parent in set or parent is root" (a rooted connected subtree containing the root), of size <= level, with every selected `requiresLevel` node satisfied by the current level. The in-game order of allocation is irrelevant (account allocation verified valid by replaying in saved order).
- Refund (`validateRefund`): allowed only if the node is allocated and **no allocated node lists it in `requires`** (`has_dependents`), i.e. only leaf nodes of the current selection can be removed. Cost: `TALENT_REFUND_CREDIT_COST = 3` reroll credits per node (Constants @3062; client checks `G.rerollCredits >= 3`, toast `insufficient_credits`), sent as `refund_talent`. There is no "respec all" button seen in the code; a full respec of n nodes costs 3n credits (up to depth ordering). Allocation itself is free. If level drops (it can't) requiresLevel is not rechecked.
- Reroll credits: starts 200 (`STARTING_REROLL_CREDITS`), +1 per task completed (`REROLL_CREDIT_PER_TASK_COMPLETE`), `REROLL_COST` 5, so refunding competes with task rerolls.

## 4. Effect types (Delve tree)

`sumEffects({delve:[ids], fortify:[ids]})` just adds `node.value` into `acc[node.effect]` (and `acc.effLevel[node.skill]` for effLevel). Everything is additive, no caps in the tree code, no diminishing returns inside it. Totals if the whole tree is bought:

| Effect id | Cluster (scope) | Total (all 120) | Node values | Mechanics, where applied |
|---|---|---|---|---|
| `effLevel` (skill) | Battle Prowess (global) | +15 levels: life 6, spirit/strike/dodge/sight/defend/draw/heft/surge/focus 1 each | medium +1 (+2 large life n109) | Adds to the "unlock bonus" of that combat skill: `getCombatBonus(skill)` (bundle @490343: `t += effLevel[skill]`) and `EffectiveLevel.unlockBonus` (`talentEffLevel`, @208145). Raises effective level (accuracy/strength/defence rolls, max HP via `getEffectiveMaxHP = LIFE_HP_MULT(2) * (life level + getCombatBonus("life"))`, spirit). Only these 10 combat skills (no vigor). |
| `minHit` | Cleave (global) | +5 | small n1 +1, medium n74 +2, n79 +2 | `getTalentCombat().minHitBonus` -> `CombatMath.computeAttack`: `H = minHitFloor(overflow, maxHit)` (= `max(1, floor(overflow*maxHit))`), then `H = min(maxHit, H + minHitBonus)`. A hit rolls uniformly in `[H, maxHit]`. `overflow = clamp(rawHitChance-1, 0, OVERFLOW_CAP)` so min hit only above the base floor when your accuracy beats the defence. So +minHit is a flat raise of the floor, capped at max hit. Applied in raid and normal combat. |
| `maxHit` | Onslaught (global) | +5 | small n2 +1, medium n45 +2, n93 +2 | `maxHitBonus`: `maxHit = t.maxHit(strScore) + bonus` (flat after the formula; with ammo penalty computed before). |
| `critChancePct` | Precision (global) | +14.5 percentage points | small 0.5 (13 nodes), medium 1 (4), large 2 (2) | `critChanceBonus = critChancePct/100 + collector + shard sets + specials armory`; final `critChance = min(1, critChance(sources) + bonus)` where base `critChance(src) = clamp((5 + 0.2*src)/100, 0..1)` (`CRIT_BASE_CHANCE_PCT 5`, `CRIT_CHANCE_PER_SOURCE_PCT 0.2`). Hard cap 100%. |
| `critDamagePct` | Savagery (global) | +33 percentage points | small 1 (13), medium 2 (4), large 4 (3) | `critDamageMult = (120 + 0.25*src) + critDamagePct (+ other sources)`; crit damage = `max(maxHit+1, floor(maxHit*mult/100))`. So tree adds +x to the 120% base (not multiplicative). |
| `attackSpeedPct` | Swiftness (global) | +5 | small 0.25 (8), medium 0.5 (2), large 1 (2) | Exposed as `getTalentCombat().attackSpeedPct` and in the Gear Calc (`_deriveDelve`, @256899), but **not applied anywhere in the client damage code** (`computeAttack` uses `weaponSpeed` and vigor only: `attackInterval = weaponSpeed*(1 - vigorReduction)`). The speed bonus is therefore applied server-side (raid/combat simulation) - exact formula UNVERIFIED (probably `interval/(1+pct/100)` or `*(1-pct/100)`; the difference at 5% is tiny). |
| `corruptChancePct` | Corruption (global) | +5 | small 0.25 (8), medium 0.5 (2), large 1 (2) | "Chance a slain mob resurrects corrupted" (cluster desc). Server-side raid mechanic; client only stores it. Effect on rewards not found in client. |
| `combatXpPct` | War Study (global) | +10 | small 0.5 (8), medium 1 (2), large 2 (2) | `getSkillXpBonus(skill)` (@~494500): for the 10 combat skills `bonus += (globalXpPct + combatXpPct)/100`. Additive with the other XP bonus sources (tools, pets, capes, collector, milestones...), added to the multiplier sum, not a separate multiplier. |
| `slayXpPct` | Hunter's Lore (global) | +10 | small 0.5 (8), medium 1 (2), large 2 (2) | Same function, skill `slay`: `+ (globalXpPct + slayXpPct)/100`. |
| `delveXpPct` | Delver's Insight (**raid** scope) | +10 | small 0.5 (6), medium 1 (3), large 2 (2) | Same function, skill `delve`: `+ (globalXpPct + delveXpPct)/100`. Cluster desc: "Delve experience gained from raid damage". Delve XP is only earned in raids. Faster delve levels -> faster point income. |
| `globalXpPct` | Revelation (global) | +10 | two large +5 (n110, n120, both require level 110) | Added to every skill's XP bonus (`N = x.globalXpPct`) before the per-category term. Fortify tree has +13.25 globalXp spread; delve's big ones are deep in the extended branches. |
| (zero in delve tree) | | | | `sumEffects` has more keys (`moveSpeedPct, successPct, saveMaterialPct, doubleGatherPct, skillingXpPct, fortifyXpPct, actionTimeSec, foodHeal, barterPanelXp`) which only the Fortify tree uses. All delve nodes only use the 11 above. |

Combat-relevant stat plumbing (client) - the full chain a planner needs:
- `G.getTalentCombat()` @500321 returns `{maxHitBonus, minHitBonus, critChanceBonus, critDamageMultBonus, attackSpeedPct}`; the `sumEffects` call there passes only the delve ids (`fortify: []`).
- `CombatMath.computeAttack(opts)` @~197400: `maxHit = t.maxHit(str)+maxHitBonus` ; `critChance = min(1, critChance(sources)+chanceBonus)`; `critDamageMult = critDamageMult(sources) + damageMultBonus*100`; `minHitFloor = min(maxHit, floor(overflow*maxHit)+minHitBonus)` (min 1); crit floor via `critFloorPct`. Hit roll: `p + floor(rand*(maxHit-p+1))` where p = min hit floor; on crit it is `critDamage(...)` of the roll... (see `resolveAttack` @199200).
- Constants (shared, @7000-10000): `CRIT_BASE_CHANCE_PCT 5`, `CRIT_BASE_DAMAGE_MULT_PCT 120`, `CRIT_CHANCE_PER_SOURCE_PCT 0.2`, `CRIT_DAMAGE_PER_SOURCE_PCT 0.25`, `VIGOR_SLOPE .0025`, `VIGOR_REDUCTION_CAP .5`, `COLLECTOR_MAX_CRIT_CHANCE_PCT 10`, `COLLECTOR_MAX_CRIT_DAMAGE_PCT 10`, `COLLECTOR_MAX_XP .1`, `LIFE_HP_MULT 2`. No cap on tree effects; the only found caps are crit chance <= 100% and min hit <= max hit.
- Accuracy: the tree has **no accuracy node**; accuracy is only affected indirectly via `effLevel` (strike/sight/focus accuracy skills, dodge/defend for defence rolls).

## 6. Open questions / unverified

1. Server-side behaviour of `attackSpeedPct` and `corruptChancePct`: the client never applies them. The formula (divide vs. subtract), rounding, and whether attack speed has a floor are unknown. Ask the dev / measure via the raid log.
2. Whether the server enforces the same rules (it almost certainly shares `raid-trees.json` and `RaidTreeEffects`; only the client call sites were seen). Server-side rule for level drop or `requiresLevel` re-check not observable.
3. How the Delve XP is awarded per damage in raids (the base of which `delveXpPct` multiplies) and the XP curve to 120 (`xpTable`, `XP_AT_EXTENDED_MAX_LEVEL 4e8`) - needed for "points over time" planning. Not researched.
4. Is there a full-reset/respec button? Only per-node refund (3 credits, leaves only). Not found in client code, may exist behind a different UI.
5. `pointsFreeStart:1` is in the JSON but unused by `pointsAvailable` (`max(0, level||1)`), so level 1 = 1 point, consistent with the account (37 points at 37). Treat as `points = level`.
6. How `critFloorPct`, `critChanceDamagePct`, penetration etc. (non-tree) interact is out of scope; `resolveAttack` details of crit application order only skimmed (@199200).
7. Hit/min-hit interplay: `minHit` only helps when `overflow>0` is not required (the bonus is added regardless: `H = min(maxHit, H + minHitBonus)`), so +5 min hit is always effective up to max hit. Marked as read from `computeAttack`; not tested in game.
